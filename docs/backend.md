# Backend

Rust: [rocket](https://rocket.rs) serving a GraphQL API built with
[juniper](https://github.com/graphql-rust/juniper), PostgreSQL 18 through diesel-async.
`moneta` is one binary and `serve` is only one of its subcommands.

Read [concepts.md](concepts.md) first — the two-layer model is what most of this file assumes.

## Layout

```
migrations/         diesel migrations. The schema, the rendered views and the analysis
                    functions all live here
src/
  bin/moneta.rs     entry point: config loading and subcommand dispatch
  cli/              user, account and periodic subcommands
  config.rs         the settings struct
  lib.rs            password hashing, connection pool, migration runner
  schema.rs         generated by `diesel print-schema`
  schema_views.rs   hand-written table! definitions for the views — they have no primary key
                    for print-schema to infer
  models/           row structs, plus models/rendering.rs for what the views return
  rendering.rs      what is left of the money maths once the views own it
  accrual.rs        reading a period off a statement, and what one instance of a template covers
  rules.rs          periodic and automation rules. The pure parts are well covered by tests
  queries.rs        shared queries, including loading and writing the expense aggregate
  graphql/          one module per domain; root.rs wires the schema and the auth.
                    investments.rs is the one that calls out, to stockdb, and writes nothing
tests/sql/          SQL assertions against a freshly migrated database
```

## The write path

An expense spans three tables (`expenses`, `expense_transactions`,
`expense_categorizations`), so **every write goes through `queries::insert_expense` or
`queries::replace_expense`** inside a `conn.transaction()`, together with its changelog entry.
`Expense::split()`/`join()` in `models/expense.rs` convert between the aggregate and its rows.

Transaction order is stored as `idx` and has to stay dense, which is why an update rewrites the
children instead of diffing them.

## GraphQL conventions

The schema is generated, checked in at `frontend/schema.graphql`, and **documented in place** —
the doc comments on the Rust types become descriptions in the SDL, so that file is the API
reference. Regenerate it with no database and no running server:

```sh
cd backend && cargo run -- schema > ../frontend/schema.graphql
```

Do not hand-edit it, and do not use `houdini pull-schema` — it needs a live backend, sorts
arguments alphabetically, and switching between the two reformats the whole file.

Both roots are namespaced one level deep: `Query.expenses.list`, `Mutation.accounts.create`.

**Lists take typed arguments.** Each names its own filter arguments, a per-entity sort enum and
a direction. There is no filter document and no query language to parse, so a caller cannot
reach a column the resolver did not offer.

`Expense.createdAt` and `Expense.updatedAt` expose the current rendered record's creation and
edit timestamps. They are not transaction value dates, booking dates, accrual endpoints or
historical changelog timestamps. Related account/category edits can change rendered content
without changing the expense's `updatedAt`.

**Authentication** accepts a signed private session cookie or an explicit
`Authorization: Bearer mk_<prefix>.<secret>` header on both GraphQL HTTP routes.
An explicit header is the sole credential, even when malformed or invalid; it never falls
back to a cookie and never creates, renews or clears cookies. Invalid credentials use
`extensions.code = "UNAUTHENTICATED"`; valid keys without permission use `FORBIDDEN`.
The frontend's login redirect keys on `UNAUTHENTICATED`, not on arbitrary backend errors.

`api_keys.rs` generates 32 random secret bytes with OS randomness, stores only a SHA-256
hash and a unique nonsecret lookup prefix, and compares hashes in constant time, including
unknown-prefix lookups. The database checks access levels (`read` and `write`) and expiry.
Every bearer request joins the owner in the database and checks expiry. Revocation physically
deletes the row; owner deletion cascades to credentials without changing financial foreign
keys. Password changes leave API keys valid.

Read keys can query, including all ordinary per-user rendering. Before execution the handler
parses the document with Juniper and identifies the selected operation by `operationName`
(or the sole operation). A selected mutation rejects the entire request, including a batch
containing one. Names, aliases and fragments cannot turn a mutation into a query. Write
keys retain existing domain ownership/visibility checks. The `users` mutation namespace
(login/logout/visit) and all `apiKeys` fields, including metadata lists, are session-only.
Guards precede resolver side effects. Write operations are not transactional as a whole:
a permitted field may commit before a later session-only field returns `FORBIDDEN`.

Successful authentication conditionally updates `last_used_at` at most once per minute,
using a database predicate rechecked under row locking across replicas. Authentication
counts even when subsequent GraphQL parsing, validation or authorization fails. Invalid or
expired keys never update it. This is usage metadata, not an audit trail.

**Per-user scoping is the resolver's own `user_id` filter** against the rendered views. Callers
have no way to express one. Where a resolver hands out something reachable by id — a rule's
template, say — it still has to check that the caller can *see* it.

Password hashes are verified with the parameters from the stored PHC string rather than with
fixed ones, which is what keeps pre-2026 argonautica hashes working alongside new argon2 ones.

### Three things that bite

- **Never hold a pool connection while awaiting a dataloader.** A loader batch takes a
  connection of its own, so a resolver holding one and asking for a second deadlocks as soon as
  there are as many concurrent requests as the pool has connections. It does not recover, and
  from outside it looks like a backend accepting requests and answering none. Scope the
  connection into a block that ends before the loader runs. `prime_many` is safe.
- **The pool is 16 with a 15-second wait timeout, and both numbers are deliberate.** A request
  holds one connection at a time, so the size caps concurrent DB-touching requests — a page
  load fires around six. `max_connections` is 100, so `16 × replicas` plus the cronjobs is the
  budget. The timeout is what makes a mistake survivable. `Timeout occurred while waiting for a
  slot` in the log is the signal to resize — or that something is nesting again.
- **A new mutation has to invalidate the analysis cache.** `analysis.balances`, `history` and
  `overviews` are memoized in process for ten minutes (`graphql/cache.rs`); financial
  mutation fields set `context.wrote`, and the handler empties the cache once the request
  is done. `users` and `apiKeys` deliberately do not: visit markers, credential management
  and authentication/last-use writes do not change financial answers.

## Migrations and SQL

Migrations are more than the schema: **the rendered views and every analysis function live in
them**. `simulate_balances`, `accrual_adjustment`, `analysis_movements`, `analysis_statement`,
`analysis_period_totals`, `analysis_category_totals` and `analysis_category_expenses` are
PostgreSQL functions defined by their own migrations.

Putting the arithmetic in a SQL function rather than in a Rust query string is deliberate: it
is the only way `tests/sql` can reach it, and that is the only place in the repo where a query
can be tested against a real database. It has already caught a missing template filter and
three ordering and weighting bugs that review had passed over.

Two performance traps live here:

- `expense_users` is a `UNION` over the whole transaction table, so **no filter on account or
  date narrows it**. Reading `expense_transactions_rendered` from inside a lateral rebuilds the
  entire rendering on every invocation — `simulate_balances` went from 1.7 s to 104 ms by
  materializing it once in a CTE and joining against that.
- **A shared expense renders once per involved user.** Reading
  `expense_transactions_rendered` without `user_id = …` double-counts every transaction of an
  expense touching two users' accounts. Filtering on `account_id` alone does not save you —
  both copies name the same account.

And one correctness trap: a **rule template carries a real account and a real date**, so
nothing but `is_template` says it never happened. Every analysis function filters it out —
`simulate_balances`, `count_balance_expenses`, `analysis_statement` and `analysis_movements`,
which the three totals functions all read from. Forgetting is invisible until a balance is
wrong by exactly one template.

An automation template keeps a **blank booking**: one transaction of exactly zero, which
`impose` drops before adding the delivered line. Two things make it necessary rather than
tidy. Its date is the phase the accrual derivation measures against, and a transactionless
expense has no owner at all — `expense_users` is a union over transactions and their accounts,
so an expense with none renders for nobody and cannot be listed or opened. The zero is what
identifies it, not its position, so a template can be edited without changing what a rule
books.

## Tests

```sh
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo test
PGURL=postgres://moneta:moneta@localhost:5499/moneta tests/run-sql-tests.sh
```

`cargo test` covers the pure logic: rule instantiation, accrual shapes and password
verification.

`TEST_DATABASE_URL=... cargo test --test scoping` exercises the per-user SQL accessors.
`TEST_DATABASE_URL=... cargo test --test api_keys` exercises the production GraphQL HTTP
handler, sessions and key lifecycle with dummy users. Both migrate and truncate fixtures,
so run them sequentially against a disposable database, or use separate databases.
`MONETA_REQUIRE_DB_TESTS=1` makes a missing URL fail the API-key suite. CI runs both in
the database-backed job, not only the DB-free unit-test job.

`tests/run-sql-tests.sh` applies every migration to an empty database and then asserts that the
views, the CHECK constraints and the analysis functions do what they claim. The views carry the
money maths, so that is where a mistake would be expensive. Point it at a **scratch** database,
not one holding real data — it migrates whatever it is given.

CI is strict: `clippy -D warnings` and `fmt --check` both fail the build, test code included.

## CLI

```sh
moneta serve                         # run the API
moneta user --add|--update|--remove <name> | --list
moneta user --stockdb-token <name>   # paste stockdb's API token on stdin; empty clears it
moneta account --list x              # the flags take a dummy value, see below
moneta account --sync <id1> <id2> [--invert x]
moneta account --unsync <id>
moneta periodic --list               # rules, and how many expenses each is due for
moneta periodic --run                # generate the expenses that are due
moneta schema                        # the GraphQL schema as SDL
```

`--list` and `--invert` on `account` are declared as value-taking options rather than flags, so
they need a throwaway argument. Worth fixing, hasn't been.
